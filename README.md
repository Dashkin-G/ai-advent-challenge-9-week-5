# RAG по правилам дорожного движения

Пятая неделя курса по ИИ-агентам, тема недели — RAG.

- **День 21** — пайплайн индексации (документ → чанки → эмбеддинги → индекс) и
  сравнение двух стратегий нарезки на вопросах с известным ответом.
- **День 22** — первый RAG-запрос: агент с двумя режимами, без RAG и с RAG, и
  10 контрольных вопросов, на которых режимы сравниваются автоматически.

## Что индексируется

**Правила дорожного движения РФ** с приложениями, действующая редакция: 121
страница, 46 разделов, 585 пунктов. Страница скачивается один раз с
[garant.ru](https://base.garant.ru/1305770/), из неё выбрасываются примечания
Гаранта и история изменений, а текст сохраняется в Markdown: `#` — часть, `##` —
раздел, `###` — подраздел, абзац пункта начинается с номера. Текст правил —
официальный документ и авторским правом не охраняется.

**Эталон для проверки поиска** — 130 вопросов экзаменационных билетов ГИБДД
(категории A, B; набор [etspring/pdd_russia](https://github.com/etspring/pdd_russia)).
Взяты вопросы без картинок, в подсказке к которым указан пункт правил, поэтому
для каждого вопроса известно, где в тексте лежит ответ.

## Две стратегии нарезки

Размер чанка у обеих общий — 1000 знаков, иначе сравнивался бы размер, а не
способ нарезки.

- **Фиксированный размер** — окно 1000 знаков с перекрытием 150. Режет где
  придётся: посреди пункта, на стыке разделов. Граница сдвигается к пробелу,
  чтобы не рвать слова.
- **По структуре** — режет только по границам пунктов и никогда не пересекает
  заголовок раздела. Мелкие пункты одного раздела собираются в чанк до 1000
  знаков, пункт длиннее 1500 делится по абзацам.

У каждого чанка метаданные: `chunk_id`, `source`, `title` (часть документа),
`section` (раздел › подраздел), `points` (номера пунктов), `start`/`end`
(позиция в тексте), `chars`, `tokens`.

## Индекс

- Эмбеддинги — `BAAI/bge-m3` локально на процессоре, 1024 измерения, bfloat16
  (на процессоре с AVX-512 в 1,75 раза быстрее float32, векторы совпадают до
  косинуса 0,998).
- Векторы — FAISS `IndexFlatIP` на каждую стратегию: векторы нормированы,
  поэтому скалярное произведение равно косинусу, поиск точный.
- Текст и метаданные чанков — SQLite. Там же кэш эмбеддингов по хешу текста:
  пересборка без изменений занимает секунды, после правки текста
  пересчитываются только изменившиеся чанки.

## Результат

130 вопросов, в выдаче — первые 5 чанков.

| | Фиксированный размер | По структуре |
|---|---|---|
| Чанков | 257 | 274 |
| Средний размер | 994 знака ≈ 229 токенов | 796 знаков ≈ 183 токена |
| Разрезано пунктов | 132 (22,6 %) | 17 (2,9 %) |
| Чанков на стыке разделов | 56 (21,8 %) | 0 |
| Нужный пункт первым | 46,2 % | **63,1 %** |
| Нужный пункт в первых 5 | 78,5 % | **83,1 %** |
| Какая часть пункта попала в 5 чанков | 77,1 % | **80,7 %** |
| Объём 5 чанков | 4 970 знаков | **4 117 знаков** |
| MRR@10 | 0,597 | **0,720** |

Нарезка по структуре ставит нужный пункт первым заметно чаще: из 34 вопросов,
где стратегии разошлись, 28 за ней (точный тест Макнемара, p < 0,001). В первой
пятёрке разница в пределах случайности (10 : 4, p = 0,18) — найти находят обе,
но структура ставит нужное выше и отдаёт модели на 17 % меньше текста.

Заодно видна хрупкость фиксированной нарезки: после удаления из текста одной
служебной строки сдвинулись все границы ниже по тексту, и доля «нужный пункт
первым» у неё упала с 50,8 % до 46,2 %. У структурной она почти не изменилась.

**Как считали.** Чанк считается нужным, если он совпадает с эталонным пунктом
хотя бы наполовину меньшего из двух: короткий пункт должен лежать в чанке хотя
бы наполовину, кусок длинного пункта — хотя бы наполовину состоять из него.

## Агент с двумя режимами

- **Без RAG** — модель отвечает по памяти.
- **С RAG** — вопрос → эмбеддинг → 5 ближайших чанков из индекса «по структуре»
  (он выиграл сравнение нарезок) → промпт «фрагменты правил + вопрос» → модель.

Инструкция в обоих режимах одна и та же: коротко, прямой ответ первым, после
утверждения — пункт в квадратных скобках. Разница только в контексте, иначе
сравнивались бы промпты, а не RAG. С RAG модели добавлено: отвечать только по
фрагментам, а если ответа в них нет — так и сказать.

Модель — `qwen3.8-2.4t-a95b` (Alibaba Model Studio, OpenAI-совместимый режим).
Ответ приходит потоком: в интерфейсе оба режима печатаются рядом, у RAG видны
шаги «поиск → промпт → модель», найденные чанки и то, что ушло модели.

## 10 контрольных вопросов

Составлены вручную — `control_questions.json`. У каждого вопроса зафиксированы
ожидание (ключевые факты, которые должны быть в ответе) и пункты-источники.
Вопросы подобраны так, чтобы проверить разные случаи, а не только удобные:

| № | Вопрос | Что проверяет | Источник |
|---|---|---|---|
| 1 | С какой скоростью можно ехать в жилой зоне? | известный факт | п. 10.2 |
| 2 | На каком расстоянии выставить знак аварийной остановки? | два числа | п. 7.2 |
| 3 | С какого возраста ребёнка можно везти спереди без кресла? | несколько условий | п. 22.9 |
| 4 | Где запрещён обгон? | длинный перечень | п. 11.4 |
| 5 | Минимальная глубина протектора летних и зимних шин? | другой документ | п. 5.4, 5.5 Перечня |
| 6 | Можно ли на электросамокате по тротуару и с какой скоростью? | два пункта | п. 24.2(1), 24.6 |
| 7 | Какого размера знак «Начинающий водитель»? | редкая деталь | п. 8 Основных положений |
| 8 | Можно ли показать права по QR-коду из телефона? | правка от 8.09.2026 | п. 2.1.1 |
| 9 | Какой штраф за проезд на красный свет? | вопрос вне базы | нет: штрафы — в КоАП |
| 10 | Можно ли ехать на красный свет? | промах поиска | п. 6.2 |

Каждый вопрос задаётся в обоих режимах, ответы проверяются автоматически:

- **верный ответ** — в нём есть все ключевые факты. Факт — регулярное выражение
  по тексту ответа (числа, термины); у вопроса вне базы верно сказать, что в
  Правилах этого нет, и не называть сумму;
- **пункт назван** — в ответе есть номер источника (10.2, но не 110.2 и не 10.20);
- **пункт в контексте** — чанк с источником попал в 5 чанков, ушедших модели.
  Если нет — неверный ответ RAG объясняется ошибкой поиска, а не модели.

Ответы хранятся как есть, проверка считается при чтении: поправили ожидание —
вердикты пересчитываются без нового обращения к модели.

### Результат

| | Без RAG | С RAG |
|---|---|---|
| Верных ответов | 6 из 10 | **9 из 10** |
| Ключевых фактов в ответах | 19 из 27 | **26 из 27** |
| Нужный пункт назван | 7 из 11 | **9 из 11** |
| Нужный пункт среди найденных чанков | — | 10 из 11 |
| Токенов на ответ: вход | **172** | 1 546 |
| …из них размышления модели | 6 121 | **1 631** |
| Токенов на ответ всего | 6 420 | **3 301** |
| Время ответа | 2 мин 56 с | **50 с** |

Режимы разошлись на 3 вопросах, все три — в пользу RAG (самокат, права по
QR-коду, штраф). На 10 вопросах это пример, а не доказательство (точный тест
Макнемара, p = 0,25).

Неожиданное: вход с RAG в 9 раз больше, но ответ вдвое дешевле и втрое быстрее —
с найденным пунктом модель почти не рассуждает, а без него долго вспоминает.

Где RAG не справился — вопрос 10 («Можно ли ехать на красный свет?»): нужного
пункта о сигналах светофора нет среди найденных чанков, и модель ответила про
железнодорожный переезд. Это ошибка поиска, а не модели.

## Запуск

```bash
pip install -r requirements.txt
python -m app.main        # http://127.0.0.1:8000
```

Для ответов модели нужен ключ: `DASHSCOPE_API_KEY=...` в файле `.env` в корне
проекта (в git не входит).

На вкладке «Индекс» — «Скачать и построить». При первом запуске модель bge-m3
(~2,3 ГБ) скачивается с Hugging Face, эмбеддинги считаются около 2,5 минуты.
Без интерфейса: `python -m app.pipeline`. Размер чанка и перекрытие меняются
переменными `CHUNK_SIZE` и `FIXED_OVERLAP`.

## Устройство

```
app/
  config.py     источники, пути, модели, размер чанка
  corpus.py     выгрузка ПДД и билетов, чистка HTML, структура текста, эталон
  chunking.py   две стратегии нарезки и метаданные чанков
  index.py      эмбеддинги bge-m3, FAISS + SQLite, кэш, поиск
  evaluate.py   метрики: форма нарезки, hit@k, MRR, покрытие, парный тест, проверка ответа
  pipeline.py   пайплайн с состоянием шагов, отчёт сравнения, поиск для интерфейса
  llm.py        вызов модели потоком (DashScope, OpenAI-совместимый режим)
  rag.py        агент с двумя режимами, прогон контрольных вопросов
  main.py       FastAPI: страница и HTTP-API
static/
  index.html    интерфейс: вкладки «Ответы модели» и «Индекс»
control_questions.json   10 контрольных вопросов с ожиданиями и источниками
```

Скачанное, очищенный текст, эталон, индекс и итог прогона лежат в `data/`
(в git не входит).
